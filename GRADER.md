Before opening the dashboard, visit the test site to populate it with real analytics events:

- Home (`index`)

### Step 2 -- Open the Reporting Dashboard

👉 **https://reporting.cse135patrick.site/login.php**

### Step 3 -- Explore the Reports

From the dashboard, open each of the three main reports:
- **Overview Report**
- **Performance Report**
- **Error Report**

Each one has charts, a summary table, key metrics, and a short written interpretation of the data.

---

### Step 4 -- Save a Report

Scroll to the bottom of any report page and click **"Save This Report"**. You'll be prompted to fill in:
- A title
- A description
- An analyst comment

Go ahead and submit it. This saved report will be used in the next step.

---

### Step 5 -- Review the Saved Report

Navigate to **Saved Reports** and open the one you just created. You should see the metadata you entered, the chart visualizations, and the analyst commentary all preserved correctly.

### Step 6 -- Export to PDF

Click **"Export PDF"** on the saved report. A downloadable PDF should be generated from the report page.

### Step 7 -- Check Viewer Permissions

## Known Limitations

I wanted to be upfront about a few areas that might look sparse depending on how the grading environment behaves:

**Sparse charts** -- Analytics data is generated by actual page visits, so if the test site hasn't been visited much before grading, some charts may not have a lot to show. Running through Step 1 a couple of times helps.

**Query parameter tracking** -- Product detail pages use URL parameters like `?id=3`, which the system treats as distinct pages. This gives granular per-product data, but it can also make the "Top Pages" table look longer than expected.

**Performance data** -- Performance metrics come from browser-reported events. If not many were generated during testing, the performance report may have a small sample size.

**Error report** -- The error trend chart only populates when actual client-side browser errors are caught. If everything runs smoothly during testing, this chart may stay minimal.

**PDF formatting** -- The export is generated from the live HTML report. Very long tables or unusually large reports could cause some layout quirks in the PDF output.

**Chart rendering** -- Charts are built with Chart.js and render client-side. They may not display in older browsers or if JavaScript is disabled.

**Collector dependency** -- All analytics rely on a JavaScript collector. If a browser blocks scripts or the collector gets disabled, events won't be recorded and reports will be empty.

**Event schema assumptions** -- Some backend queries assume a consistent event format from the collector. Unexpected or malformed events could affect how data gets aggregated.

## Architectural Considerations

### Query Parameter Tracking

Pages with query parameters (like `product-detail.html?id=5`) are tracked as unique URLs. This is useful for granular product-level analytics, but it does increase the number of distinct URLs stored in the database. In larger systems, URLs are typically normalized before aggregation to avoid this kind of fragmentation.

---

### Collector Trust Model

The analytics collector accepts client-side data as-is, which means a malicious client could theoretically submit fabricated events. For the scope of this project, there's no request validation, rate limiting, bot detection, or event signing in place. A production system would need server-side verification and some form of abuse prevention.

---

### Authentication

Authentication uses server-side sessions with role-based access checks on report pages. This works well here, but larger systems generally move toward token-based authentication, OAuth providers, or centralized auth services for better scalability and cross-system integration.

---

### Report Rendering

Reports are rendered with server-side PHP queries and client-side Chart.js visualizations. This made development fast and kept things flexible, but at scale it puts repeated load on the database whenever reports are accessed. Larger systems typically introduce precomputed dashboards, materialized views, or caching layers to handle concurrent users more efficiently.

Also,
Saved reports store report configuration rather than a snapshot of analytics data. 
Charts are generated dynamically when the report is viewed, meaning the visualizations reflect the most current dataset rather than the state at the time the report was saved.

A production reporting system would likely store snapshot data to preserve historical accuracy of reports.

I recognize this as a drawback and might be misleading. I want to make it clear that when saving these reports, the data visualization doesn't reflect previous "state".

---

### Analytics Data Model

The system stores raw events and computes all metrics at query time. An alternative approach would use separate event streams, analytics pipelines, or an OLAP data warehouse, which opens the door to more advanced reporting and better historical analysis at scale.

---

### PDF Export

PDFs are generated by converting report pages directly into downloadable files. This works fine for normal-sized reports, but very large datasets or highly dynamic dashboards could run into formatting issues. Production systems typically handle this with dedicated reporting services or background processing queues rather than on-the-fly conversion.
